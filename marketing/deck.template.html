Diagrams that can't go stale

ortho renders six architecture views straight from SysML v2 text. No drawing tool, no cloud service, no model repository — a model file, one command, and an SVG you commit next to the code.

npx ortho render models/logical.sysml -d logical -o diagrams/logical-view.svg

The problem

The drawing is the first thing to lie

  • An architecture diagram drawn by hand is a snapshot of an intention. Rename a component in the code and the picture keeps the old name — silently, indefinitely.
  • The picture lives in a binary file that only one person has the license to open, so it gets redrawn on demand rather than kept true.
  • Reviewers can't diff it. A pull request shows the model changed and the diagram changed, but not whether they agree.
  • So teams stop trusting diagrams, and the architecture goes back to living in people's heads.

The approach

One file per view. Six views. One command each.

  • The text is the source of truth. Functions, components, ports and scenarios are written in SysML v2 — the OMG standard notation, not an invented DSL.
  • Diagrams are build artifacts. Regenerate them like you compile code; never edit an SVG by hand.
  • CI keeps them honest. Re-render in the pipeline and fail on a dirty git diff — a stale diagram becomes a broken build.

Change a component

part controller : RadioController;

Every view that shows it updates

npm run diagrams git diff --exit-code diagrams/

Each view is written in its own model file and rendered from it, so scoping is something you can see in the file tree. The six SVGs on the following sheets came out of exactly this command. Nothing was touched by hand.

RenderSVG text
  • No browser anywhere. SVG is written as text, so there is no headless Chrome to install, sandbox, or wait for.
  • No LLM at render time. The same model always produces the same bytes — diagrams diff cleanly.
  • Real text metrics. Font advance widths are embedded, so boxes fit their labels without measuring in a DOM.
  • Two dependencies do the heavy lifting: a parser generator and a layout engine. Both plain npm packages.

package Software {

    // Each module says which function it realizes.
    package Flight {
        private import Software::FlightPlatform;

        // AP_Mission
        part def MissionExecutor {
            perform survey.guideNavigateAndControl.guide;
        }

        // AP_Motors
        part def FlightControl {
            perform survey.guideNavigateAndControl.control;
        }

        // GCS_MAVLink
        part def MavlinkInterface {
            perform survey.communicate.exchangeTelemetry;
        }

Deployment view

Which hardware runs which software

examples/survey-drone/deployment.sysml
// This file declares nothing of its own. Its whole
// content is the mapping between the other two.
package Deployment {

    private import Software::*;
    private import Hardware::*;

    // The firmware has the control computer
    // to itself, kernel included.
    allocate Software::sw.mission
        to Hardware::system.drone.fc;
    allocate Software::sw.control
        to Hardware::system.drone.fc;
    allocate Software::sw.rtos
        to Hardware::system.drone.fc;

    // Every container shares the GPU computer.
    allocate Software::sw.planner
        to Hardware::system.drone.companion;
    allocate Software::sw.zenoh
        to Hardware::system.drone.companion;

    allocate Software::sw.app
        to Hardware::system.ground.tablet;
}

Process view

Mark an area, upload it, fly it

examples/survey-drone/process.sysml
action def SurveyMission {
    part operator;
    part app : Software::Ground::SurveyPlanner;
    part bridge : Software::Middleware::MavlinkBridge;
    part mavlink : Software::Flight::MavlinkInterface;
    part mission : Software::Flight::MissionExecutor;

    message markArea from operator to app;
    then message approve from operator to app;

    // MAVLink's mission protocol: the vehicle
    // asks for each item in turn.
    then message missionCount of MissionCount
        from bridge to mavlink;
    then message requestItem of MissionRequestInt
        from mavlink to bridge;
    then message missionItem of MissionItemInt
        from bridge to mavlink;
    then message missionAck of MissionAck
        from mavlink to bridge;

    then message startAuto from mavlink to mission;
    then message flySurveyLegs
        from mission to mission;
}

Self-contained

Runs anywhere Node runs

  • No external programs. No Enterprise Architect, no Graphviz binary, no headless browser. Node 24+ and nothing else.
  • No network at render time. Nothing is uploaded; models never leave the machine. Air-gapped builds work.
  • Deterministic output. The same model produces the same bytes, so an SVG diff means the architecture actually changed.
  • Installs as a dev dependency. It lives in node_modules and writes only where you point it — the tool's own sources never mix with yours.
  • {{TESTS}} tests cover the grammar, every view extractor, layout and end-to-end rendering of both reference models.
  • Programmatic API too, if you would rather call the pipeline than the CLI.

Install

npm install --save-dev ../path/to/ortho

Render

npx ortho render models/logical.sysml \ -d logical \ -o diagrams/logical-view.svg

Keep honest
